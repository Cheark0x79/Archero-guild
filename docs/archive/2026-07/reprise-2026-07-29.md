Cette note conserve les sujets à reprendre demain et la direction proposée pour
séparer la capture/OCR locale de l'application de production.

## État au 28 juillet

Terminé et testé :

- normalisation adaptative et OCR membres/boss, y compris podium ;
- OCR Lab limité explicitement à la machine locale ;
- contrat JSON v1 partagé dans `contracts/import-batch.schema.json` ;
- construction locale d'un lot et publication HTTPS ;
- validation distante avec contrôle qualité à 100 % ;
- import PostgreSQL transactionnel et idempotent ;
- image plateforme sans ADB/Tesseract et image OCR séparée ;
- affichage et association manuelle des identités non résolues ;
- navigation commune stabilisée entre les pages du dashboard.

À faire ensuite :

- ajouter la consultation API de l'historique et du statut des imports ;
- intégrer la commande lot/validation/publication aux boutons de l'agent local ;
- mettre en place et tester les sauvegardes/restaurations ;
- extraire physiquement le composant OCR vers son dépôt une fois le contrat
  confirmé sur plusieurs imports réels.

## Décisions à conserver

- BlueStacks, ADB, la normalisation des images et Tesseract tournent sur le PC
  de confiance.
- Tesseract ne tourne pas sur le serveur principal de production.
- Les données ne sont plus publiées avec un commit Git contenant les résultats
  d'import.
- Le PC n'accède jamais directement à PostgreSQL.
- Le PC envoie uniquement un lot JSON structuré et validé à une API
  d'ingestion HTTPS de la production.
- La production revalide le lot et l'écrit dans PostgreSQL dans une transaction
  atomique.
- Les captures brutes restent des artefacts d'audit et ne sont pas nécessaires
  au fonctionnement quotidien du site.

## Sujets fonctionnels à traiter demain

### 1. Navigation lente et accès Admin instable

Symptôme : pendant un changement de page, la partie Admin disparaît puis
réapparaît après le chargement.

À vérifier :

- chargement asynchrone de `/api/auth/session` à chaque navigation ;
- rechargement complet provoqué par les liens HTML au lieu d'une navigation
  client ;
- nouvelle récupération de `/api/dashboard-data` sur chaque page ;
- état initial `sessionRole = null`, qui masque temporairement les entrées
  réservées à l'administrateur ;
- temps de réponse de l'API et de PostgreSQL.

Résultat attendu : conserver la session et les données communes pendant la
navigation, afficher un état de chargement stable et ne jamais faire
disparaître brièvement un accès déjà autorisé.

### 2. Membres sans identifiant

- Afficher les lignes OCR sans `playerId` dans Members et Check.
- Permettre d'ouvrir une fiche temporaire basée sur un identifiant interne
  immuable.
- Ajouter une action admin « Associer un ID ».
- Montrer les suggestions de correspondance sans appliquer automatiquement une
  association incertaine.
- Conserver qui a effectué l'association, quand, et depuis quelle capture.
- Réappliquer l'association aux imports historiques compatibles.

Ne pas utiliser le nom comme clé primaire : il peut changer et l'OCR peut le
lire différemment.

### 3. Entrées, sorties et renommages

Prévoir des états explicites :

- `active` : présent dans la dernière capture complète ;
- `new` : nouvel ID ou nouvelle identité non encore confirmée ;
- `unmatched` : ligne lisible mais sans ID associé ;
- `left` : absent de plusieurs captures complètes consécutives ;
- `former` : départ confirmé et conservé dans l'historique ;
- `renamed` : même ID, nouveau nom confirmé.

Un membre ne doit pas être marqué parti à cause d'une capture incomplète ou
d'un échec OCR. Le changement d'état doit dépendre d'un import accepté et, pour
un départ, de plusieurs observations ou d'une validation admin.

### 4. Historique incomplet dans la fiche membre

Cas observé : la fiche de Pignouf n'affiche que le 27 juillet alors que Check
contient des lignes plus anciennes.

À comparer :

- clé utilisée par la fiche : `playerId`, nom ou alias ;
- source utilisée : snapshots courants, snapshots bruts ou PostgreSQL ;
- filtres qui excluent les anciennes lignes ;
- variations de nom et lignes historiques sans ID ;
- fusion entre données importées en JSON et données chargées depuis la DB.

La source de vérité cible doit être PostgreSQL. Check et Member doivent lire les
mêmes snapshots via des vues ou requêtes communes.

## Architecture OCR locale vers production

```text
PC de confiance
  BlueStacks + ADB
        |
        v
  captures PNG immuables
        |
        v
  normalisation + Tesseract + validation locale
        |
        v
  lot JSON versionné + hash + clé d'idempotence
        |
        | HTTPS + jeton d'ingestion limité
        v
Production
  API d'ingestion admin
        |
        +--> validation du schéma et dry-run
        +--> détection des doublons
        +--> transaction PostgreSQL
        +--> journal d'audit
        |
        v
  dashboard et API de lecture
```

### Contrat du lot

Le lot envoyé par le PC doit contenir au minimum :

```json
{
  "schemaVersion": 1,
  "captureDate": "2026-07-29",
  "generatedAt": "2026-07-29T22:15:00+02:00",
  "agentVersion": "git-sha-ou-version",
  "idempotencyKey": "2026-07-29:sha256-du-lot",
  "sourceImages": [
    {
      "kind": "guild-members",
      "sha256": "...",
      "width": 1440,
      "height": 2560,
      "detectedRows": 5
    }
  ],
  "members": [],
  "bossRankings": [],
  "quality": {
    "status": "pass",
    "coverage": 1,
    "completeness": 1,
    "warnings": []
  }
}
```

Le schéma doit être versionné et partagé par le client local et l'API de
production.

### API proposée

- `POST /api/v1/imports/validate` : dry-run, aucune écriture.
- `POST /api/v1/imports` : publication atomique du même lot.
- `GET /api/v1/imports/{id}` : statut et rapport (à ajouter).
- `GET /api/v1/imports?date=YYYY-MM-DD` : historique et audit (à ajouter).

Le serveur doit :

1. authentifier un jeton réservé à l'ingestion ;
2. limiter la taille et le débit ;
3. valider le JSON et sa version ;
4. vérifier la clé d'idempotence ;
5. refuser une couverture insuffisante ou des rangs incohérents ;
6. créer un enregistrement d'import en staging ;
7. écrire membres, snapshots et boss dans une transaction ;
8. marquer le lot publié uniquement après le commit ;
9. conserver le rapport et les hashes pour l'audit.

Une nouvelle tentative avec la même clé doit retourner le résultat existant et
ne jamais dupliquer les statistiques.

### Commande locale cible

```text
archero-sync capture --date 2026-07-29
archero-sync validate --date 2026-07-29 --target production
archero-sync publish --date 2026-07-29 --target production
```

La publication automatique pourra venir ensuite, mais le premier workflow doit
garder une validation humaine avant l'écriture en production.

### Sécurité

- Ne jamais publier le port PostgreSQL.
- Utiliser HTTPS via Cloudflare Tunnel.
- Créer un jeton distinct des comptes utilisateur/admin.
- Limiter ce jeton à l'ingestion et permettre sa révocation.
- Stocker le secret localement hors Git.
- Ajouter éventuellement un Cloudflare Access Service Token ou du mTLS.
- Journaliser l'identité du client, la date, le hash du lot et le résultat.
- Ne pas accepter de chemins de fichiers fournis par le client.

## Sauvegardes et restauration

### Données à protéger

- PostgreSQL ;
- rapports d'import JSON ;
- associations manuelles entre lignes OCR et IDs ;
- règles et validations humaines ;
- captures brutes si elles doivent permettre un nouvel OCR ;
- version applicative et version du schéma ayant produit chaque import.

### Politique initiale

- dump PostgreSQL quotidien au format custom ;
- sauvegarde avant chaque migration ;
- sauvegarde chiffrée des rapports et captures avec Restic ;
- copie hors du serveur principal ;
- rétention : 7 quotidiennes, 4 hebdomadaires, 12 mensuelles ;
- contrôle quotidien de présence et de taille ;
- test de restauration mensuel dans une DB temporaire.

Un snapshot Proxmox complète ces sauvegardes, mais ne remplace pas le dump
PostgreSQL ni la copie hors machine.

### Critère de restauration

Une restauration est considérée valide uniquement si elle permet de :

1. restaurer PostgreSQL dans une instance vide ;
2. redémarrer une version compatible de l'application ;
3. retrouver les membres et leur historique ;
4. retrouver les imports et associations manuelles ;
5. comparer le nombre de snapshots avec le rapport sauvegardé.

## Déploiement futur : staging, images immuables et ArgoCD

Cette phase vient après la stabilisation de l'import.

### Environnements

| Environnement | Base | Données |
| --- | --- | --- |
| Développement | PostgreSQL locale | données de test |
| Staging | DB séparée | copie anonymisée ou jeu contrôlé |
| Production | DB dédiée | données réelles |

Ne jamais partager la même base entre staging et production.

### Chaîne cible

1. CI exécute les tests et construit une image.
2. L'image est publiée dans GHCR avec le SHA Git.
3. Les manifests Helm ou Kustomize référencent ce tag immuable.
4. ArgoCD synchronise d'abord staging.
5. Les migrations sont exécutées comme un Job contrôlé.
6. Les vérifications de santé et un test d'import dry-run passent.
7. La version est promue en production.
8. Le rollback applicatif réutilise l'image précédente.

Pour les migrations DB, un rollback applicatif ne suffit pas. Toute migration
destructive exige une sauvegarde, une procédure de retour et, si possible, une
évolution compatible avec l'ancienne et la nouvelle version.

### Secrets et sauvegardes dans la cible GitOps

- SOPS + Age pour les secrets GitOps ;
- clé Age sauvegardée hors cluster ;
- PostgreSQL sur stockage persistant ou VM dédiée ;
- backups indépendants du cluster ;
- restauration testée dans un namespace ou une VM temporaire ;
- ArgoCD ne gère pas les données : il gère seulement l'état déclaratif des
  applications.
